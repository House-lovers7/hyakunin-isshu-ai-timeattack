# 百人一首AIタイムアタック 統合企画書

作成日 2026年9月20日  
版 1.0  
状態 実装前の提案仕様。実測結果および開発実績はまだない。

## 1 企画の目的と結論

同じ百人一首の読み上げを受けた専用プログラムとJevが、どの段階で、どれだけ速く、どれだけ正しく札を取るかを比較する。取得の瞬間を札の飛散、衝撃、効果音で見せ、判断の違いを観客が体感できるタイムアタックにする。

仮称は「百人一首AIタイムアタック」。説明文は「プログラムとAIは、どこまで聞けば、どれだけ速く札を取れるのか」。

この企画の中心は、同じ課題と演出で異なる解き方を並べることにある。専用プログラムが圧勝する結果にも価値がある。決まった処理にAIを使う費用や待ち時間を、実測で説明できるためである。Jevの速度、誤り、待つ判断も、そのまま結果として見せる。

もう一つの成果物は開発過程である。要件定義、設計、モデル選定、セッション数、トークン、料金、人間の作業時間、やり直しを記録し、完成品の品質と結び付けて公開する。企画力と設計力は、勝敗を望む方向へ誘導することではなく、比較の妥当性と結果の分かりやすさで示す。

### これまでの会話から維持する内容

| 内容 | 扱い |
|---|---|
| 百人一首の読み上げ途中で札を取る | 企画の中心として維持 |
| 専用プログラムとJevを両方作る | 初期版の必須要件 |
| 速さと精度とお手つきを比較する | 成績画面と測定の中心 |
| 取得の瞬間に「バン」と感じる演出 | 初期版の必須要件 |
| タイムアタックモード | 初期版の主モード |
| 開発時のAI利用量とモデル選定理由を見せる | 開発初日から記録 |
| 人間や日本記録の速さと比べたい | 人間の同条件実測から開始。公式記録は未確認 |
| 作り手の構想力と設計力を示す | 企画目的として維持。能力全般を断定する試験とはしない |

本書で追加したラウンド数、締切、画面構成、開発順序などは推奨案であり、会話で確定した事実とは区別する。

## 2 誰に何を伝えるか

| 相手 | 体験から伝えること | 確認する方法 |
|---|---|---|
| AIに詳しくない観客 | AIが判断する速さと、誤る可能性 | 一首の映像と成績だけで違いを説明できるか |
| エンジニア | ルールで解く部分、モデルに判断させる部分の違い | 入力条件、計測、コード、再現ログを確認できるか |
| 開発を依頼する人や協業相手 | 企画を完成条件へ落とし込み、費用も管理できること | 設計判断と開発実績が対応しているか |

初期版は技術紹介と実績公開を主目的にする。継続的なゲーム需要や課金需要はまだ検証していない。反応を見る前に、本格的な学習サービスやオンライン対戦サービスへ広げない。

## 3 比較対象と順序

| 対象 | 役割 | 導入段階 |
|---|---|---|
| 専用プログラム | 読みを前方一致で照合し、一意に決まれば取得する比較基準 | 初期版で必須 |
| Jev | 公開された入力から札または待機を選ぶ | 初期版で必須 |
| 通常のLLM 1モデル | Jevと別のAI方式を比較する | 第2段階 |
| 人間 | 同じアプリ上での挑戦と最高記録 | 第2段階 |
| 音声から判断する各構成 | 音声認識を含む実用上の速度を比較する | 第3段階 |

専用プログラムとの比較だけで「Jevは他のAIより速い」とは結論しない。AI間の違いを述べる場合は、同じ課題を通常のLLMにも解かせる。

専用プログラムの結果は、その実装と入力条件での結果である。「全てのプログラムが全てのAIに勝つ」という一般化はしない。百首を走査する単純な実装から始め、必要な場合にのみTrieなどの構造へ変える。単純な走査でも要件を満たすなら、その判断自体を設計記録に残す。

## 4 一回の体験

### 画面構成

最初は横長の観戦画面を作る。上部に読み上げの進行、中央に左右二つの同じ札盤、下部に取得結果を置く。

| 位置 | 表示内容 | 方針 |
|---|---|---|
| 上部 | 今読み上げられた部分、音声の進行 | 未来の文字を表示しない |
| 左側 | 専用プログラムの札盤と取得演出 | Jev側と同じ札・配置 |
| 右側 | Jevの札盤と取得演出 | 専用プログラム側と同じ札・配置 |
| 下部 | 正解数、お手つき数、今回の取得時間 | まず三つの結果が読めることを優先 |
| 結果画面 | 全問の成績、遅延分布、費用、実験条件 | 詳細は試合後に開ける |

札は下の句を基本表示とし、取得された札を拡大して読み取れるようにする。候補数を減らした展示用レイアウトを作る場合は、100候補の測定と記録を分ける。札の表示数だけ減らし、裏で100候補を選ばせる場合は、観客がそれを分かる表示にする。

### ラウンドの流れ

1. 同じ札配置を両側に表示する。
2. 読み上げを開始し、公開済みの音に対応する読み文字を順に入力する。
3. 各方式は「札を取る」または「まだ待つ」を判断する。
4. 取得を確定した時刻を先に記録する。
5. 正解なら札が飛び、衝撃と短い効果音を出す。間違いなら別の演出と「お手つき」を出す。
6. もう一方は、自分の独立した盤面で判断を続ける。先に取得されたことを理由に測定を打ち切らない。
7. 両方の判断が終わるか締切に達したら、取得時刻と判断に使った読みの長さを並べる。
8. 次の問題へ進む。終了後、全ラウンドの成績を表示する。

### 演出の設計

| 場面 | 演出案 | 守ること |
|---|---|---|
| 正解 | 札が盤外へ飛ぶ、接点に衝撃、短い打撃音 | 両方式に同じ強さの演出を使う |
| お手つき | 札が短く震える、異なる音、「お手つき」の文字 | 正解と色だけで区別しない |
| 見送り | 待機状態から「時間切れ」を表示 | 誤答と区別する |
| API障害 | 「取得できず 通信エラー」などの結果表示 | モデルの誤答と区別する |
| 接戦 | 二者の取得地点を時間軸に残す | 表示精度より細かい差で勝敗を作らない |
| リプレイ | 同じ記録をスロー再生し、取得の順序を見せる | 再生倍率を明記し、実測時間を書き換えない |

高速すぎて違いが見えない場合は、実測ログに基づくスロー再生で見せる。遅い側が有利に見えるような人工的な待ち時間は入れない。お手つきが起きなかった場合もそのまま公開し、失敗を演出のために作らない。UI確認用の模擬データは「模擬」と表示し、本番成績から除く。

人間が挑戦する画面では、他方式の取得札や正誤を自分の回答前に見せない。先行するAIの演出が答えのヒントになるためである。観戦用画面や終了後リプレイでは全者を重ねてよい。

## 5 初期版のルール

通常の競技かるたの全ルールを再現するのではなく、百人一首を用いた独自の比較用タイムアタックとする。空札、送り札、陣地の駆け引きは初期版に入れない。

| 項目 | 推奨する初期仕様 |
|---|---|
| 候補 | 全100首。両者に同じ読みと札IDの対応表を与える |
| 1問の出題 | 百首の中から一首を読む |
| ラウンド独立性 | 毎問100候補へ戻す。過去の取得による候補の減少を使わない |
| 回答 | 札IDを一つ選択するか待つ |
| 取得権 | 各方式、一問につき取得は一回。誤答後の連打・取り直しは不可 |
| 締切 | 初期案は上の句の読み上げ終了から2秒後。実験設定に固定して記録 |
| 展示用 | 10問。短い紹介動画はその中の3問程度を使う |
| 測定用 | 100首を各1回評価し、時間変動の確認用に3回まで反復する初期案 |
| 順序 | 順序を変更して実行。エンジンへ未来の出題順や生成用seedを渡さない |
| 初期設定 | プロンプト、閾値、締切、公開頻度を成績計測前に固定 |

全首を網羅する測定では、エンジンを毎問リセットし、既出の首や残り問題から答えを推定できないようにする。人間用の100問挑戦は各問を独立抽選し、同じ首が再登場し得ると説明する。「100問」と「全100首を一度ずつ取る」は同じものとして扱わない。

### 順位の考え方

結果の主表示は「正解数、お手つき数、取得時間」の併記とする。速さだけの単一スコアで総合性能を主張しない。

各問では正解した方式の取得時刻を比較する。誤答した方式は、その問の早取りの勝者にはならない。画面上の得点は正しく先に取った回数として表示できるが、精度の評価には各者の独立した回答を全て使う。

人間向けの記録としては「100問全問正解での取得時間合計」を別に設ける。失敗した挑戦も正解数とお手つき数を保存する。同じ設定・入力部門・端末条件の記録を比較し、先読み成功を含む記録かどうかも区別する。

## 6 入力を二段階に分ける

### 初期版 読み上げに同期した文字入力

観客は読み上げを聞き、両エンジンは同じタイミングで公開された読み文字を受け取る。初期版のAIは音を直接聞かない。この事実は開始画面と比較条件に短く表示する。

読みは音声に対応する仮名へ正規化する。歴史的仮名遣いの表記差が、一方だけに有利な入力にならないようにする。画面に使う原文と機械に渡す読みは別フィールドとして保持する。

1音相当の単位が公開されるごとに入力を更新する。単位は実装時に固定し、初期案は読みのモーラ単位とする。音声との対応時刻を手作業でも点検し、音が出る前に未来の文字を配信しない。公開時刻は認識可能性の科学的な厳密境界ではなく、この実験で定めた境界である。

静的な百首の一覧は教材として両者に見せてよい。秘密にするのは、今回の正解札ID、まだ公開していない続き、出題順などである。モデルに毎回全候補を渡す費用も実測に含める。

この部門から言えることは、同じ文字情報を受けた各構成の判断と応答の違いである。人間の聴覚や生音声の認識能力まで比較したとは言わない。

### 拡張版 音声認識を含める

同じ音声を共通の音声認識へ送り、時刻付きの認識結果を両方式に渡す。途中の認識結果の修正も、両者へ同じように渡す。認識の誤り、認識の待ち時間、認識後の判断時間を分けて記録する。

人間は音声と画面からタップし、ソフトは音声認識後に札IDを選ぶ。これは各構成の体験上の比較として示し、人間の手の移動とモデルの内部処理を同じ能力だと説明しない。

さらに構成全体を自由にする競技を作る場合は、専用の音声照合、補正付きの文字照合、音声対応モデルなども別枠で参加できる。ただし、初期版の順位へ混ぜない。

## 7 Jevに任せる範囲

Jevの公式ドキュメントでは、Choiceは定めた選択肢から一つを選び、選択結果、各候補の確率、確信度を返す。最大255選択肢なので、本企画の「100札と待機」の101選択肢は仕様上収まる。ただし日本語の百人一首での正確さと速度は未検証である。[Choiceの公式仕様](https://docs.typesafe.ai/primitives/choice)

| 部分 | 担当 |
|---|---|
| 今回どの札を選ぶか、または待つか | Jev |
| 音声再生、入力の公開、タイマー | 通常のコード |
| 正解との照合、取得を一回に制限する処理 | 通常のコード |
| 演出、集計、保存 | 通常のコード |
| 低い確信度で待つなどの行動条件 | 事前に固定した方針をコードで適用 |

推奨する初期の質問は一つとする。「これまでに公開された読みから、取る札を選ぶ。十分な情報がなければ待機を選ぶ」。候補の説明には各札の読みを同じ形式で入れる。全首を一つのChoiceで扱い、100回の別リクエストには分けない。

AI側だけ専用コードで正しい候補を先に特定し、その答えをJevに確認させる構成にはしない。その構成を後で試すなら「コードとAIの混合方式」として別に測る。

### 待つ判断の見せ方

標準設定を固定してまず計測する。拡張として、取得に必要な確信度の閾値を変え、急いで取る設定と慎重に待つ設定の成績を比較する。閾値は調整用データで選び、本番データに合わせて後から都合よく変更しない。

公式のconfidenceは確率分布の集中度から計算される値で、正答率そのものではない。画面では「モデルの確信度」と「実測の正解率」を別に表示し、confidenceが0.9だから正解率90%という表記はしない。[確信度の公式説明](https://docs.typesafe.ai/confidence)

初期版の観戦画面では、確信度を必須表示にしない。詳細画面またはリプレイで、判断に使った入力と一緒に示す。途中の予測を表示する場合も、モデルが実際に返した時点の値だけを使い、架空の思考や迷いのアニメーションを作らない。

## 8 計測設計

### 二つの試験

| 試験 | 方法 | 分かること |
|---|---|---|
| 固定入力での試験 | 読みの途中を一つの固定入力として各方式へ与える | 同じ情報量での選択、待機、応答時間 |
| ライブ逐次試験 | 読み上げとともに入力を更新する | 更新頻度、通信待ち、待機方針を含めた実際の取り方 |

前者はライブの勝負そのものではなく、結果の理由を調べるための測定である。ライブでは方式ごとに処理中に届く入力が違うため、両方を用意すると「少ない情報で判断したのか」「情報は来ていたが応答が遅かったのか」を区別できる。

### 時刻の定義

時刻の差は共通の計測主体の単調増加時計で取る。別の端末やAPIサーバーの時計を直接引き算しない。

初期版のライブ比較では、観戦ブラウザが両方式への送信、応答の受信、取得確定、表示を同じ時計で記録する案を採用する。両方式は共通のサーバー窓口を通し、サーバー内の処理時間はそのサーバー自身が測った経過時間として別途返す。音声の再生時計との対応と再生開始のずれも確認する。画面上の取得時刻は、外部API内部で計算が終わった時刻そのものではない。

| 記号 | 定義 |
|---|---|
| t_start | 問題の読み上げ開始 |
| t_unique | 公開文字列だけで、100候補の中から一意に特定できる最初の公開時刻 |
| t_snapshot | あるリクエストに含めた最新の入力が公開された時刻 |
| t_dispatch | そのリクエストを送った時刻 |
| t_response | 使用可能な応答全体を受け取った時刻 |
| t_commit | 有効な取得が確定した時刻 |
| t_present | 取得エフェクトを画面へ出した時刻 |

| 指標 | 定義 | 読み方 |
|---|---|---|
| 読み始めからの取得時間 | t_commit − t_start | 観客に見える勝負の時間 |
| 特定可能になってからの取得時間 | t_commit − t_unique | 必要な情報がそろってからの遅れ。負なら先読み |
| 問い合わせの往復時間 | t_response − t_dispatch | Jevは通信とサービス処理を含む |
| 問い合わせ開始までの待ち | t_dispatch − t_snapshot | スケジュールや同時実行制限の影響 |
| 表示までの遅れ | t_present − t_commit | フロント側の処理と描画 |
| 判断に使った情報量 | リクエストに含めた読みの長さと版 | 応答到着時に聞こえていた長さとは区別 |

t_uniqueは評価用の注釈であり、Jevが呼ばれるタイミングをそこだけに絞るための答え情報として使わない。意味理解や人間の聴覚の最速限界を示す時刻でもない。

Jevの公式紹介には70〜500msという応答時間の説明があるが、測定は主に米国西海岸で行った旨の記載もある。本企画の日本からの応答時間、100候補を含む入力、実際の負荷で保証される値ではない。企画書の予測値として転記せず、実測する。[公式の性能説明と測定条件](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

### 正確さの集計

各問を、正解 C、誤答 W、見送り M、技術エラー E のいずれか一つへ分類する。合計問題数 N = C + W + M + E とする。

| 指標 | 計算・表示 |
|---|---|
| 全問に対する正解率 | C / N |
| 取得したときの正解率 | C / (C + W)。取得ゼロなら未定義と表示 |
| 取得率 | (C + W) / N |
| お手つき率 | W / N |
| 見送り率 | M / N |
| 技術エラー率 | E / N |
| 取得時間 | 正解分の中央値と遅い側の95パーセンタイル。対象件数も併記 |
| 費用 | 全試行の費用、1問当たり、正解取得1件当たり。正解ゼロの単価は未定義 |

慎重に待ち続けた方式が「正解率100%」だけで強く見えないよう、全問に対する正解率と見送りを必ず出す。タイムアウトや通信障害を集計から隠さない。方式間の速度差を見るときは、両者が正解した同じ問題の差も併記する。

一度も間違えなかった場合は「今回のN問で誤答0件」と表現する。将来も間違えない、正解率が厳密に100%である、とは言わない。

### 誤りを調べる分類

| 分類 | 判定の考え方 |
|---|---|
| 曖昧な段階での先読み失敗 | 取得に使った入力では候補が複数残っていた |
| 特定可能な入力での選択ミス | 取得に使った入力では正解が一つに定まっていた |
| 入力の認識・正規化の問題 | 音声認識や読みデータの段階で入力が変わった |
| 実装・通信の問題 | 不正な応答、締切超過、接続失敗、状態混入など |

誤りの分類には、取得時の時計だけでなく、その判断が参照した入力の版を使う。古い曖昧な入力への応答が遅れて到着したケースを、十分な情報を見た上での誤答に分類しない。

## 9 比較の公平性

1. 百首データ、読みの正規化、候補の順序、公開する入力と公開予定をそろえる。
2. 全文や正解IDを、現在の出題の情報としてモデルへ渡さない。教材の候補一覧と今回の正解情報を分離する。
3. 専用プログラムにもJevにも同じ問題を解かせる。Jevだけに困難な札を出すなどの操作をしない。
4. 全方式が同じ呼び出し管理を通る。専用プログラムの単体処理時間と、Jevの通信込み時間は別の内訳として残す。
5. APIキーとAPIへの通信はサーバー側で扱い、ブラウザへキーを渡さない。
6. ライブ逐次試験は一方式につき処理中リクエスト最大1件を初期方針とする。新しい入力は最新の1件へまとめ、応答後に次を送る。取りこぼした更新数を記録する。
7. 最大同時実行数や入力更新頻度を変えた場合は、別設定の記録として扱う。呼び出しを増やして速くした場合、その費用も出す。
8. 終了済み問題への遅着応答は採用しない。すでに取得済みの判断を後から正解に差し替えない。
9. 他者の答えと判定はエンジンへ渡さない。人間の操作画面でも回答前の答え漏れを防ぐ。
10. モデル版、設定、プロンプト、計測地域、端末、回線条件、日時を保存する。ウォームアップの有無、再利用接続、キャッシュ状況も分かる範囲で記録する。
11. 最速の一回だけではなく、全件とばらつきを出す。選んだ見どころ動画から、全件の結果へたどれるようにする。
12. 画面表示は計測精度に合わせる。計測できない細かさで順位や「0ms」を表記しない。

取得しなかった入力更新も実験条件の一部である。ライブ逐次試験の順位は、モデル単体ではなく、呼び出し方針を含む構成全体の成績として説明する。

## 10 人間の記録と日本記録

現時点で、このアプリの計測条件と一致する公式な日本最速記録は確認できていない。未確認の秒数をベンチマークへ入れない。全日本かるた協会の公式情報は、競技や読み方の参照先として利用する。[全日本かるた協会](https://www.karuta.or.jp/)

人間との比較は次の順に進める。

1. 同じアプリで自分が挑戦し、端末と入力条件を記録する。
2. 経験者にも同じ環境で挑戦してもらい、「本企画の実測記録」として掲載する。
3. 名人・クイーンなどの選手に協力いただける場合も、その称号と本企画での実測値を別々に表示する。
4. 外部の速度データが見つかったら、測定開始点、停止点、音声条件、手の移動、標本数、認定元を確認する。

画面上の推奨表記は「このアプリの人間最高記録」または「協力選手の実測」。公式な認定と条件が確認できるまで「日本記録」とは表示しない。

初心者・経験者の違いを測る企画は面白さを増やし得るが、人間に100候補の札IDを瞬時に返す機械と同じ運動条件を要求しない。比較している単位が、頭脳そのものか、音声からクリックまでのシステムかを混同しない。

## 11 実装の構成

ブラウザで遊べる一つのアプリを初期案とする。TypeScriptのフロントとサーバーに、データ、入力配信、判断、評価、演出、記録の責務を分ける。JevはHTTP APIから接続できる。[公式Quick start](https://docs.typesafe.ai/introduction/quickstart)

| 部品 | 責務 |
|---|---|
| 百首データ | 原文、正規化した読み、札ID、表示内容、音声と公開時刻の対応 |
| 出題管理 | 正解、問題順、音声再生予定、制限時間。答え情報を保持する |
| 入力配信 | 公開済みの読みだけを時刻と版付きで配信 |
| 判断アダプター | 専用コード、Jev、後日のLLMへ同じ状態を渡す |
| 判定管理 | 最初の取得を確定し、正誤・見送り・技術エラーを記録 |
| 観戦画面 | 判定済みイベントから演出を再生 |
| 実験ログ | 全入力、応答、料金、設定、結果を保存して再生可能にする |

判断エンジンは「問題番号、公開された読み、候補一覧、入力版」を受け取り、「札IDまたは待機、参照した入力版、利用量、取得可能な確率情報」を返す。正解、未来の音声、出題seedは受け取らない。

初期版は利用者登録や大規模なランキングDBを必須にしない。実験単位のJSONLと集計CSVを保存し、同じログから成績とリプレイを生成できればよい。後でWeb上に記録を公開する場合は、成績に実験設定IDを持たせる。

### 実験ログに残す項目

| 区分 | 主な項目 |
|---|---|
| 実験 | 実験ID、入力部門、日時、コード版、データ版、設定版 |
| 条件 | モデル名と返却された版、閾値、プロンプト版、候補順序、公開頻度、締切 |
| 入力 | 問題ID、入力版、公開済み文字列、公開時刻、送信時刻 |
| 応答 | 応答時刻、選択札、待機、確率、確信度、エラー、再試行 |
| 判定 | 取得時刻、正誤、入力の曖昧さ、見送り、誤りの分類 |
| 費用 | 入出力トークン、取得できる場合のキャッシュ利用量、単価の参照日、実際の料金 |
| 表示 | 演出を出した時刻、実測／再生／模擬の区分 |

## 12 開発そのものを測る

### 開発用モデルの選定方針

「一番安いモデルで全て行う」ことを目標にしない。品質と完成条件を固定し、それを達成する総費用と時間で選ぶ。

| 作業 | 初期の選定方針 | 切り替える条件 |
|---|---|---|
| 比較条件、時刻、答え漏れ、状態管理の設計 | 推論と設計レビューに強いモデルを短い範囲で使う | 要件の矛盾や検証漏れが残る場合 |
| 型定義、定型UI、表示の整備 | 小型または低費用モデルを試す | 必須条件を満たせず修正が重なる場合 |
| 非同期処理、課金管理、不具合修正 | 問題の難度に合わせて選ぶ | 同じ原因の失敗が続く場合 |
| 原文と読みの確認 | 信頼できる資料と人間の確認を中心にする | モデルの自己申告だけで正確としない |
| 文言、説明、デモ構成 | 小さな入力と明確な出力条件で作る | 観客が結果を誤解する場合 |

モデル名と料金を先に固定した「最適解」とは呼ばない。小さな代表タスクで実績を取り、成功した作業当たりの費用と人間の修正時間から選ぶ。利用中の契約で測れない項目は未計測とし、架空のトークン数を埋めない。

### 開発台帳

| 項目 | 記録内容 |
|---|---|
| タスク | 目的、完成条件、変更範囲 |
| モデルとツール | 実際に利用した名称、版、選定理由 |
| セッション | セッションID、開始終了、対応するタスク |
| 利用量 | 入出力トークン、取得可能ならキャッシュ読書き量 |
| 料金 | 実際の従量料金、通貨、価格表の参照日 |
| 人間の時間 | 指示、レビュー、修正、データ確認に使った時間 |
| 結果 | 採用した変更、完成条件の達成、差し戻し、不具合 |
| 検証 | 実行した必要な確認と結果 |

セッション数は利用実態を説明する補助指標であり、少ないほど優れているとは限らない。短いセッションに分割すると総入力が減る場合も、仕様の伝え直しが増える場合もある。

開発用の生成AI料金と、完成したアプリがJevを呼ぶ運用料金を分ける。定額契約は月額の固定費として示し、按分した参考額を出す場合は計算方法を併記する。従量料金と定額の按分額を無意識に二重計上しない。為替換算する場合は換算日とレートを残す。

運用費の見積もりは、小規模実測で得た「一問当たりの呼び出し数 × 一回当たりの実請求額 × 問題数」を起点にする。再試行、取得後に残った呼び出し、音声認識やサーバーの費用も別項目で加える。キャッシュの効き方や単価が変わる場合は条件を更新する。専用プログラムは外部AI料金がなくても、全ての運用費がゼロという表記にはしない。

開発用APIの上限と、一回の測定に使うAPIの上限を別々に設定する。段階0の後に上限額、想定問題数、最大呼び出し数を決め、上限に達したら未完了の試行を明示して停止する。現在は利用量が未測定のため、確定した予算額は置いていない。

### トークンとやり直しを減らす具体策

- 共通の仕様、入出力、完成条件を短い参照文書へ固定し、作業ごとに変更範囲だけを渡す。
- 一つのタスクを小さくし、必要なファイルとログだけを文脈へ入れる。
- 毎回の長い会話要約の代わりに、決定済み事項と未解決事項を更新する。
- 料金だけでなく、差し戻しと人間の修正時間を見てモデルを切り替える。
- 画面の細部より先に、計測と答え漏れのない構成を完成させる。
- 同じ入力への呼び出しや、取得後の無用な呼び出しを止める。停止後も課金される処理は費用へ含める。

一度の開発だけで「あらゆる選択肢の中で最小コストだった」とは主張しない。言えるのは、採用したモデル構成の実績と、試した代替案との差である。

| 段階 | 作るもの | 次へ進む条件 |
|---|---|---|
| 0 前提確認 | Jevへの接続確認、101選択肢の小規模確認、数首の読みデータ | 返却仕様、費用の取得可否、待機の扱いを確認できる |
| 1 計測の最小構成 | 共通の入力配信、専用照合、Jevアダプター、ログ | 同じ入力から各者の取得時刻と正誤が保存される |
| 2 一首の観戦体験 | 二つの札盤、読み上げ、取得とお手つき演出 | ログの結果と表示の順番が一致する |
| 3 全首でのタイムアタック | 百首データ、10問展示、全首測定、成績 | 試合全体の結果が再集計できる |

| 5 比較対象の追加 | 通常のLLM、人間の挑戦 | 初期版と混同しない条件・成績を持てる |

Jevの利用可否や実データの準備が未確認のため、現段階で完成日と実費を断定しない。段階0の確認後、実装とデータ整備を分けて見積もる。APIを使えない間の画面開発は模擬応答で進められるが、Jevの実測デモとしては公開しない。

### 初期版で必ず確認すること

- 全100首のIDと読みが一対一に対応し、表示する札が一致する。
- 一意に決まる前の同じ接頭辞で、照合側が勝手に正解を選ばない。
- 同じ入力を受けた各方式に、答えや未来の読みが漏れない。
- 一度取得した札を後から変更できず、終了後の遅着応答が次問へ混ざらない。
- お手つき、見送り、技術エラーが別々に計上される。
- 判定時刻が演出の長さに影響されない。
- 実験ログから同じ成績を再生成できる。
- AIの呼び出し上限と費用の上限で停止できる。

これらは比較の信用を守る検証である。見た目の細かい変更ごとに大規模な検証を追加する必要はない。

## 14 リスクと方針を変える条件

| 起こり得ること | 意味 | 対応 |
|---|---|---|
| 専用プログラムが全勝する | 固定ルールに専用処理が適したという結果 | 結果を隠さず、Jevの実測差と費用を説明 |
| Jevがお手つきしない | この試行条件では誤答が観測されなかった | 0件と公開。故意に誤りを作らない |
| Jevが極端に誤る | 課題、入力表記、質問、モデルの適合性を要点検 | 調整用データで原因確認し、変更後を別版で測定 |
| 音声認識の待ちが支配的 | モデルの判断速度の違いが見えにくい | 同期文字部門を残して内訳を説明 |
| 速さの違いが肉眼で見えない | 通常再生だけでは伝わらない | 同じログのスロー再生と時間軸を追加 |
| 観客が「AIは無意味」とだけ受け取る | 適用範囲の説明不足 | 固定照合課題の結果だと明示。別の意味判断課題は将来の別企画 |
| API呼び出し数が増えすぎる | 更新単位と非同期処理の設計に無駄がある | 最新入力の集約、取得後の停止、上限管理 |
| 実装範囲が広がりすぎる | 計測より対戦基盤に工数を使っている | 初期版の二者・一人観戦・ログ保存へ戻す |
| 日本記録が確認できない | 外部の速度との公正な比較ができない | 同アプリでの実測最高記録を採用 |

企画の継続判断は、Jevが勝ったかでは決めない。再現できる比較が完成し、観客が結果を理解できるなら主目的は達成する。Jevの実APIを使えない、入力条件をそろえられない、費用の上限を管理できない場合は、本番の公開計測へ進まない。

理解の小さな確認として、初見の5人程度に短い映像を見てもらい、「どちらが速かったか」「どちらが間違えたか」「何を比較した結果か」を説明してもらう。これは画面と説明を直すための確認であり、市場需要を証明する調査ではない。

## 15 公開時に見せるもの

完成品と開発過程を一緒に見せる。

1. 一首のリアルタイム対戦。比較の意味が最初の数秒で分かるようにする。
2. 特徴が出たラウンドのスロー再生。実測から作り、選んだ理由を説明する。
3. 全件の正解率、お手つき、見送り、速度の分布、費用。
4. 同じ入力をどう処理したかが分かる構成図と設定。
5. 開発に使ったモデル、セッション、トークン、料金、人間の時間。
6. 設計の変更履歴。「予想と違った結果」と「次に変える点」。

60〜90秒の紹介動画では、冒頭に実際の取得、次に時間軸の再生、最後に成績と作り分けの理由を置く。説明のために全十問を詰め込まない。事前に勝敗の台本を決めず、結果が出てから構成する。

この題材で示せる設計力は、問題を整理する力、適切な比較対象を置く力、遅延を分解する力、予算内で実装する力、結果を誤解なく伝える力である。エンジニアとしての能力全体を単一の勝率から判定する企画にはしない。

## 16 最初の実装依頼に渡す要約

百人一首のタイムアタックをブラウザ向けに作る。専用プログラムとJevは同じ100候補と、読み上げに同期した途中の読み文字を受け取る。各問は独立し、取得は一度だけ。取得を確定した時刻と正誤を先に保存し、画面では同じ札盤上に取得またはお手つきの演出を出す。両者が取得するか締切まで計測し、正解数、お手つき、見送り、技術エラー、取得時間、運用費を表示する。

Jevには101選択肢のChoiceを使う案から検証する。正解や未来の読みは渡さない。初期版は生音声をJevへ送らず、音声は同期再生する。人間・通常のLLM・音声認識の追加は、初期版の測定と演出が完成してから行う。

開発の初日から、作業別のモデル選定理由、セッション数、トークン、従量料金、定額費、人間の作業時間を残す。完成条件は、百首データの正確性、同じ入力、正しい時刻計測、答え漏れの防止、成績を再生成できるログ、比較が理解できる演出である。
