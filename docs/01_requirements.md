# 01 要件定義（D2）

対象: 百人一首AIタイムアタック 初期版（ルールエンジン vs TypeSafe AI Jev、文字入力同期部門）。
出典: `docs/00_proposal.md`（企画書 v1.0、以下「§n」）と `docs/plan_review.md` の裁定表（以下「裁定#n」）。

## この文書の役割

- **何を満たせば初期版が完成と言えるか**を、検証可能な受入条件と test ID に落とす。
- 型定義・API スキーマ・画面ワイヤーは書かない（D3〜D6 と実コードが正本）。ここに書くのは「実装がどうであれ成り立っていなければならないこと」だけ。
- 企画書に書かれていない判断は入れない。企画書の外から持ち込んだ前提は「明示の仮定」として節末に分けて書く。

## 採番方針

- `R-xx` は本文書で新規に採番する要件 ID。既存文書に `R-xx` の使用例はない（`ADR-0001` 等の部分一致を除く）。
- `T-xx` は D8（`docs/07_test_plan.md`）が Vitest ファイル名へ 1:1 対応させる test ID。**T-01〜T-10 は r1 で先に予約済みなので踏襲する**（P1 Gate が「T-01〜T-08 緑」、P2 Gate が T-09、P3 Gate が T-10）。本文書は T-11 以降を新規採番した。
- §13 必須8項目は T-01〜T-08 に順番どおり対応させる。ただし**項目7（ログからの再生成）だけは T-07 と T-10 の2つを持つ**: T-07 は P1 段階の単体再集計、T-10 は P3 の100首×3通し再集計。scope が違うので別ファイル・別 ID とし、D8 の 1:1 規則は壊さない。

## 1. 札データ（§5, §6, §12）

| ID | 要件 | 受入条件 | 検証 |
|---|---|---|---|
| R-01 | 全100首のマスタを持ち、`id` 1..100 が一意で、各首が原文（上/下）・作者・正規化かな読み・画像・出典を持つ | マスタが100件、`id` 重複0、必須フィールド欠落0、読みのモーラ配列が空の首が0件 | T-01 |
| R-02 | 画面に出す原文と機械へ渡す正規化読みを別フィールドで保持し、正規化は音に合わせる（ぢ→じ、づ→ず、ゐ→い、ゑ→え、を→お、助詞「は」→わ、語中の ひふへほ→いうえお、長音はかるた読み） | 正規化関数が規則表の全ケースで期待値を返し、原文フィールドには正規化を適用しない | T-01 |
| R-03 | 決まり字長は読みから**派生計算**する（手入力しない）。分布を仮説値 1字7 / 2字42 / 3字37 / 4字6 / 5字2 / 6字6 と突き合わせ、不一致の首を列挙する。マスタのメタに `expected_source: "hypothesis"` と実測分布を持つ | 派生値が全100首で計算でき、分布が仮説と一致しない場合はテストが不一致の首 ID を列挙して落ちる（自己申告で「正しい」としない） | T-01 |
| R-04 | 両側の盤面が同じ札集合・同じ配置・同じ候補順（`id_asc`）で描かれる | 同一 config から生成した左右盤面の札 ID 列が一致する | T-01 |

裁定#24: 分布の数値は企画書に出典がなく Fable 想起値。データ生成時の機械ゲートで実測に置き換え、不一致なら数値とデータの両方を人間が確認する。

## 2. ラウンドと取得の規則（§5）

| ID | 要件 | 受入条件 | 検証 |
|---|---|---|---|
| R-05 | ラウンド独立。毎問 100 候補へ戻し、過去の取得による候補減少を使わない | 連続実行した全ラウンドで候補数が常に 100 | T-02 |
| R-06 | 照合側は、公開済み読みの前方一致候補が**ちょうど1件のときだけ**取る。複数残る段階では取らない | 決まり字長未満の全接頭辞で `wait`、決まり字長ちょうどで `take`。100首全件で正解100・お手つき0 | T-02 |
| R-07 | 各方式、1問につき取得は1回。誤答後の取り直し・連打をしない | 取得確定後に届いた応答が結果を書き換えない | T-04 |
| R-08 | 締切は上の句読み上げ終了から 2000ms（実験設定として固定・記録）。締切後の応答はログに遅着として残し、結果に採用しない。遅着が次問へ混ざらない | 締切後応答が当問の結果を変えず、次問の結果にも現れない | T-04 |
| R-09 | 展示は10問、測定は100首を各1回（時間変動の確認用に最大3反復）。「100問」と「全100首を一度ずつ」を同じものとして表記しない | モードごとの出題数が設定値と一致し、画面と文書で両者を言い分ける | T-12 |
| R-10 | プロンプト版・閾値・締切・入力更新頻度は**成績計測の前に固定**し、設定版として記録する。本番データを見てから変更しない | 実験記録に全項目が入り、途中で変えた場合は別の設定版になる | T-12 |

非スコープ（§5 冒頭）: 空札、送り札、陣地の駆け引き。

## 3. 入力の公開と答え漏れ防止（§6, §9-2, §9-9）

| ID | 要件 | 受入条件 | 検証 |
|---|---|---|---|
| R-11 | エンジンへ渡す入力に、今回の正解・出題順・生成 seed を含めない | 送信ペイロードに当該キーが存在しない（混入ゼロを直接検査する） | T-03 |
| R-12 | 未来の読みを配信しない。公開は1モーラ単位で、公開時刻に達したモーラだけを渡す | 任意時刻の公開文字列が、その時刻までに公開済みのモーラ数と一致し、先行しない | T-03 |
| R-13 | 他方式の回答・判定をエンジンへ渡さない。人間が挑戦する画面では、自分の回答が確定するまで他方式の取得札・正誤を見せない | 人間モードの画面に、回答確定前の他者結果が描画されない | T-03 |
| R-14 | 正規化した読みは両方式へ同一の文字列として渡す（表記差が一方だけの有利にならない） | 同一ラウンド・同一版で両方式へ渡った文字列が一致 | T-03 |
| R-15 | 一意特定時刻（t_unique）は評価用の注釈であり、エンジンへ渡さない。呼び出しタイミングをそこへ合わせることにも使わない | エンジンへの入力に含まれない（R-11 と同じ検査で担保） | T-03 |

静的な百首一覧は教材として両者に見せてよい（§6）。秘密にするのは今回の正解、未公開の続き、出題順。

## 4. 時刻と計測（§8）

| ID | 要件 | 受入条件 | 検証 |
|---|---|---|---|
| R-16 | t_start / t_unique / t_snapshot / t_dispatch / t_response / t_commit / t_present を、呼び出し主体の**単一の単調増加時計**で記録する。別端末・API サーバーの時計を差し引かない。サーバー内の処理時間はサーバー自身が測った経過時間として別に返す | 記録された全時刻が同一時計由来で単調。サーバー経過時間と往復時間が別の値として保存される | T-06 |
| R-17 | 取得確定時刻は有効応答を受け取った時点で決まり、**演出の長さに影響されない** | 演出時間の設定を変えても取得確定時刻が変わらない（表示時刻だけが動く） | T-06 |
| R-18 | 全方式が同じ呼び出し窓口を通る。照合側の単体処理時間と、Jev の通信込み時間を別の内訳として残す | 全リクエストが同一経路を通り、内訳の2値が欠けない | T-06 |
| R-19 | 処理中リクエストは1方式につき最大1件。新しい入力は最新1件へ集約し、応答後に次を送る。取りこぼした更新数を記録する | 同時実行が1を超えず、取りこぼし数が 0 件でも列として出る | T-15 |

企画書§8 の「70〜500ms」は公式の別条件の値であり、予測値として転記せず実測する。

## 5. 集計と誤りの分類（§8）

| ID | 要件 | 受入条件 | 検証 |
|---|---|---|---|
| R-20 | 各問を 正解 / お手つき / 見送り / 技術エラー のいずれか1つへ分類し、合計が問題数に一致する。4種を別々に計上する | 全ラウンドがちょうど1分類を持ち、4種の合計が N に一致 | T-05 |
| R-21 | 指標として 全問正解率、取得時の正解率（取得ゼロは「未定義」表示）、取得率、お手つき率、見送り率、技術エラー率、取得時間の中央値と95パーセンタイル（対象件数併記）、費用（全体 / 1問 / 正解1件、正解ゼロは未定義）を出す | 取得ゼロ・正解ゼロの入力で「未定義」を返し、0 で割った値を出さない | T-05 |
| R-22 | 誤りを「曖昧な段階での先読み失敗 / 特定可能な入力での選択ミス / 入力の認識・正規化の問題 / 実装・通信の問題」へ分類する。判定には取得時刻ではなく**その判断が参照した入力の版**を使う | 古い曖昧な入力への遅れた応答が「十分な情報を見た上での誤答」に分類されない | T-05 |
| R-23 | 追記ログを正本とし、集計結果は派生とする。ログから同じ成績を再生成できる | 保存済みログを再集計した結果が、保存された集計結果と一致 | T-07 / T-10 |
| R-24 | 集計に、再試行回数（本構成では常に0）・遅着応答数・エラー種別ごとの件数・取りこぼした更新数を**列として必ず出す**（0件でも 0 を出して空欄にしない） | 当該列が欠落せず、0 件の実験でも 0 が入る | T-07 |
| R-25 | 最速の1回だけでなく全件とばらつきを出し、見どころから全件の結果へたどれる | 結果に全問の表と分布が含まれ、抜粋から全件へのリンクがある | T-10 |

裁定#21: 再試行はしない方針だが、費用内訳を空欄にしないため列は必ず出す。

## 6. 実験モードと再現性（§5, §8, 裁定#32, 裁定#34）

| ID | 要件 | 受入条件 | 検証 |
|---|---|---|---|
| R-26 | 実験モードは 展示 / 測定 / **固定入力** / 模擬 の4種を持つ | モード値が4種に限定され、記録に残る | T-11 |
| R-27 | 固定入力試験は、各首の読みを前方 k モーラで切った固定入力を全方式へ1回ずつ与える。時計・締切を使わず、入力版は 1 に固定する。k は 決まり字長 / 決まり字長+1 / 明示の数値 から指定できる | 固定入力実行で、1ラウンドあたり各方式1リクエスト、入力版が全件1、時刻系指標が「未計測」として出る | T-11 |

| R-29 | 実験ごとに モデル版・設定・プロンプト版・計測地域・端末・回線条件・日時・ウォームアップの有無を保存する。各応答に返却モデル版（Jev は応答のモデル文字列、照合側と模擬はコード版）を持つ | 実験記録と応答記録に当該項目が入り、欠けた場合は「未計測」と明示される | T-16 |

## 明示の仮定（企画書に書かれていないが初期版で置く前提）

1. 初期版の読み上げは合成したモーラ時計で行い、実録音は段階6（音声認識の追加）と同時に導入する。企画書§13 は実録音の導入時期を固定していない（裁定#3、ADR-0006）。
2. 候補一覧は設定版に紐づくサーバー側の定数として持ち、エンジンへの入力の型からは外す。照合の関数は候補一覧を引数で受け取るため §11 の「候補一覧を受け取る」は満たす（裁定#17、ADR-0003）。
3. 公開サイトは記録の再生と説明のみを出し、実測はローカルで行う（ADR-0004）。
4. ローマ字入力版のプロンプト比較は較正セット限定で行い、本番計測前に1版へ固定する。

## 非スコープ（初期版に入れない）

- 空札・送り札・陣地の駆け引き（§5）
- 音声認識を含む部門（§6 拡張版、段階6）
- 通常の LLM・人間の挑戦（§13 段階5）。人間の記録と日本記録の扱い（§10）も初期版の順位には混ぜない
- 実録音の読み上げ（上記「明示の仮定」1）

## 保留（ユーザー判断が要るもの）

| 項目 | 状態 |
|---|---|
| 確信度の閾値 | 閾値なしを既定とし、閾値版は段階0の較正で決めて本番計測前に固定する（§7）。値は未定 |
| 決まり字長の分布 | 仮説値のまま。データ生成時の機械ゲートで実測に置き換える（裁定#24） |
| 予算の確定額 | 段階0の実測後にユーザーが決める（裁定#31） |
| 開発台帳の Acceptance 5 | 裁定#33 の「Fable main 行は2行」に対し、r6 が Fable で起動されたため3行目が発生済み。裁定を改訂するか未達のままにするかはユーザーの決定 |
